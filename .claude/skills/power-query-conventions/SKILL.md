# Power Query (M) conventions

See also `../best-practices/SKILL.md` — this file implements the team's
Power Query conventions from
`docs/best-practices/power-bi-best-practices.md`; if the two ever disagree,
the best-practices doc wins. One relevant team nuance up front: the team's
default is to source from a data warehouse and keep Power Query
transformation light. That default is now the **normal case** for this
agent's projects too, not the exception — see
`../databricks-ingestion/SKILL.md` for the connector and profiling details.
The file-sourced, Power Query-heavy approach below is still valid for the
explicit "small report sourced from files" exception the best-practices doc
carves out (`../sharepoint-data-ingestion/SKILL.md`), just no longer the
default.

## Step naming

Name every step for what it does, not `#"Changed Type1"` autogenerated
noise:

```m
let
    Source = Csv.Document(File.Contents(SourceFilePath), [Delimiter=",", Encoding=65001]),
    PromotedHeaders = Table.PromoteHeaders(Source, [PromoteAllScalars=true]),
    RenamedColumns = Table.RenameColumns(PromotedHeaders, {{"Cust ID", "CustomerKey"}}),
    TypedColumns = Table.TransformColumnTypes(RenamedColumns, {
        {"CustomerKey", Int64.Type},
        {"OrderDate", type date},
        {"Amount", type number}
    }),
    RemovedErrorRows = Table.RemoveRowsWithErrors(TypedColumns, {"CustomerKey"}),
    Result = RemovedErrorRows
in
    Result
```

- Always end with a step literally named `Result` bound in the `in` clause —
  makes diffs cleaner when steps are inserted/reordered.
- One transformation concern per step. Don't chain five `Table.` calls into
  one step just because M allows nested function calls — it makes the diff
  and the intent unreadable.

## Type everything explicitly

Never leave a column as `Any` (shown as the generic `ABC123` icon in the
Power Query UI) or rely on the default "Detect Data Types." Every column
that survives to the final `Result` step must have an explicit type set via
`Table.TransformColumnTypes`. Untyped columns silently break DAX
aggregation and relationships.

## Organization, at project scale

Once a project has more than a handful of queries:

- **Don't hand-author `queryGroup:` / `PBI_QueryGroups`.** Confirmed
  against real Power BI Desktop (June 2026 release): a hand-written
  `queryGroup:` on a partition/expression, paired with a hand-written
  `PBI_QueryGroups` annotation on `model.tmdl` defining the group
  folders by GUID, fails to deserialize at all —
  `Cannot resolve all the paths while de-serializing Database`, with every
  `queryGroup` reference unresolvable. Query-group folders in the Power
  Query navigator are purely a Desktop-UI convenience with no query-folding
  or correctness impact, so it isn't worth hand-authoring: leave queries
  ungrouped, and organize them into folders by hand in Desktop's Query
  Editor after the project opens, if wanted.
- Combine similar mechanical steps rather than one step per tiny action —
  e.g. rename every column that needs it in one `Table.RenameColumns` call,
  not five sequential single-column renames.
- Filter rows as early in the step sequence as practical — filtering before
  expensive transforms (joins, type conversions on wide tables) is both
  faster and keeps **query folding** possible for longer when the source
  supports it (e.g. a database/OData source; folding doesn't apply to flat
  file sources like CSV/XLSX, but the ordering habit still matters when
  sources change later).
- If a source table is only needed as a staging step (e.g. before a merge)
  and shouldn't appear as its own table in the model, disable "Enable load"
  for it — represented in TMDL by simply not creating a corresponding
  `partition`/table in the semantic model for staging-only queries.

## Data quality steps go before modeling, and get logged

If profiling (CLAUDE.md §3, step 2) turned up blanks, duplicates, or
inconsistent formats, handle them explicitly and visibly:

- `Table.RemoveRowsWithErrors` / `Table.SelectRows` with a clear predicate —
  not a silent `Table.Distinct` dropped in without comment.
- If rows are being dropped or values defaulted, note the count/rationale in
  the project's `NOTES.md` or `ANALYSIS.md` — a data-quality call that
  materially changes totals (e.g. "dropped 40 rows with no CustomerKey") is
  worth a line in the write-up, even if it didn't rise to a full
  `docs/decisions/` entry.

## Parameters over hardcoded values

Prefer Power Query parameters for anything that varies between environments
or that a human might reasonably want to swap without touching M code —
most importantly, don't hardcode an absolute local path inside an M
expression. Define a parameter (e.g. `SourceFolderPath`) once in
`<ProjectName>.SemanticModel/definition/expressions.tmdl` and reference it
from each table's `source =` expression. This keeps the project portable
when data moves (e.g. once SharePoint ingestion — see
`../sharepoint-data-ingestion/SKILL.md` — replaces a manual file drop) and
lets Desktop point at a small sample while a real deployment points
elsewhere without editing the M itself. The same applies to any
threshold/date-range boundary the assignment implies might change.

## Common patterns

- **Star-schema surrogate keys**: if a dimension lacks a clean natural key,
  generate one (`Table.AddIndexColumn`) rather than joining fact-to-dimension
  on a composite or fuzzy key.
- **Date dimension**: build `Date` from `List.Dates` spanning the fact
  table's min/max date (plus a small buffer), not a hardcoded fixed range —
  keeps it correct as new data arrives.
- **Unpivoting wide data**: if a source file has one column per period (e.g.
  monthly columns), use `Table.UnpivotOtherColumns` to normalize into a
  proper fact grain before modeling — don't model it wide.
