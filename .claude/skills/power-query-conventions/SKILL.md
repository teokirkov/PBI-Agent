# Power Query (M) conventions

## Step naming

Name every step for what it does, not `#"Changed Type1"` autogenerated
noise:

```m
let
    Source = Csv.Document(File.Contents(SourceFilePath), [Delimiter=",", Encoding=65001]),
    PromotedHeaders = Table.PromoteHeaders(Source, [PromoteAllScalars=true]),
    RenamedColumns = Table.RenameColumns(PromotedHeaders, {{"Cust ID", "CustomerKey"}}),
    TypedColumns = Table.TransformColumnTypes(RenamedColumns, {
        {"CustomerKey", Int64.Type},
        {"OrderDate", type date},
        {"Amount", type number}
    }),
    RemovedErrorRows = Table.RemoveRowsWithErrors(TypedColumns, {"CustomerKey"}),
    Result = RemovedErrorRows
in
    Result
```

- Always end with a step literally named `Result` bound in the `in` clause —
  makes diffs cleaner when steps are inserted/reordered.
- One transformation concern per step. Don't chain five `Table.` calls into
  one step just because M allows nested function calls — it makes the diff
  and the intent unreadable.

## Type everything explicitly

Never leave a column as `Any` or rely on the default "Detect Data Types."
Every column that survives to the final `Result` step must have an explicit
type set via `Table.TransformColumnTypes`. Untyped columns silently break
DAX aggregation and relationships.

## Data quality steps go before modeling, and get logged

If profiling (CLAUDE.md §3, step 2) turned up blanks, duplicates, or
inconsistent formats, handle them explicitly and visibly:

- `Table.RemoveRowsWithErrors` / `Table.SelectRows` with a clear predicate —
  not a silent `Table.Distinct` dropped in without comment.
- If rows are being dropped or values defaulted, note the count/rationale in
  the project's `NOTES.md` or `ANALYSIS.md` — a data-quality call that
  materially changes totals (e.g. "dropped 40 rows with no CustomerKey") is
  worth a line in the write-up, even if it didn't rise to a full
  `docs/decisions/` entry.

## Keep source-file access parameterized

Don't hardcode an absolute local path inside the M expression if it can be
avoided. Prefer a Power Query parameter (e.g. `SourceFolderPath`) referenced
from each table's `source =` expression, defined once in
`<ProjectName>.SemanticModel/definition/expressions.tmdl`. This keeps the
project portable when data moves (e.g. once SharePoint ingestion — see
`../sharepoint-data-ingestion/SKILL.md` — replaces a manual file drop).

## Common patterns

- **Star-schema surrogate keys**: if a dimension lacks a clean natural key,
  generate one (`Table.AddIndexColumn`) rather than joining fact-to-dimension
  on a composite or fuzzy key.
- **Date dimension**: build `Dim Date` from `List.Dates` spanning the fact
  table's min/max date (plus a small buffer), not a hardcoded fixed range —
  keeps it correct as new data arrives.
- **Unpivoting wide data**: if a source file has one column per period (e.g.
  monthly columns), use `Table.UnpivotOtherColumns` to normalize into a
  proper fact grain before modeling — don't model it wide.
